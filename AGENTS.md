# Architecture rules

- Kanban automations (Kommo Digital Pipeline style): per stage, trigger (on enter, after time in stage via `leads.stage_entered_at`, on enter with tag, on tag added) → AND conditions → ordered actions (move, tags, temperature, Gmail email from a template, lead schedule with Google sync, note). Pure rules in `src/lib/automations/rules.ts`; execution in `engine.server.ts` with the admin client, same-organization check, a unique `automation_runs` claim per stage pass, journey entries and max 3 chained runs. Fired from `moveLead`, `upsertLead`, `setLeadTags`, the lead webhook and public forms; time triggers run on pipeline open (throttled) and via the secret-protected `/api/public/hooks/run-automations`.
- "Won" has one definition (`lead-status.ts`): converted to client, won stage, or a "ganho" funnel tag. Leads lists non-won; Clients shows won leads with the lead card, journey and tasks. The commercial report filters client-side with `report-filters.ts`.
- Project templates are edited as dates and stored as offsets (`template-dates.ts`), so applying a template recalculates from the project start; brand colors come from the logo via `useBrandPalette`.

- There is a single calendar (`/agenda`, with Google Calendar); `/tarefas` keeps List and Kanban and redirects to it for the calendar view, both linked by `TasksViewSwitch`. Items open in place on the calendar. Google sync is immediate per change (`syncTasksNow`/`unsyncTaskFromCalendar` via `useGoogleTaskSync`); the general backfill only sends missing/changed tasks from 30 days back, in parallel, at most every 15 minutes. Task mirrors (`task_communications.metadata.mirror`) and lead schedule events are never shown twice.

- Lead schedules follow a Kommo-style loop in one shared component (`LeadTaskActions`, used by the lead card and the schedule dialog): dated observations append to `lead_tasks.notes`, "Tarefa concluída" completes with an optional result and can schedule the next action in the same server call (`completeLeadTask`, reusing `saveLeadTask` for Google Calendar sync). Journey entries: database triggers log created/done; server functions add `task_note`, `task_result` and `next_action`.

- Agenda and Tasks read pending items through one shared hook (`usePendingItems`) with the same query keys, so any change refreshes both; agenda server events only add meetings and Google Calendar (`skipPending`). Overdue, all-day and priority rules live in `src/lib/tasks/pending.ts`, and every mutation refreshes through `invalidatePendingQueries`.
- Priority alerts are read by an authenticated server function scoped to the active organization and the caller's responsibility; "CIENTE" acknowledgements are stored per user and item in `task_priority_acks` (RLS: own rows only), with a browser-local fallback until migration 21 is applied. Lead cards open globally through `LeadCardHost`/`openLeadCard`, reusing the pipeline `LeadDrawer`.

- Task date filters use one shared local-calendar-day predicate on the merged task display data so List, Kanban and Calendar apply identical inclusive deadline ranges without changing source records.

- The task center merges general tasks and lead schedules through a source-aware display adapter; lead schedules remain in their existing table, tenant-scoped through their parent lead, and use existing scheduling mutations rather than general-task actions.

- Pipeline floating navigation controls the existing board scroll container and observes its size and scroll position; it never changes lead movement or stage ordering.

- Project detail sections use the shared Tabs controls, keeping the project header and alerts visible outside the panels to preserve context.
- Project evolution reads relational stages through the existing authenticated stage function and shared project-stages query key, so roadmap updates refresh the same progress data without introducing new storage or mutation logic.
- Internal roadmap orientations share existing stage/task queries, mutations and dialogs; browser-local layout preference is separate from the portal to avoid coupling their access models.
- Public signup trials are provisioned atomically by a database auth trigger into existing organization tables; server-generated expiry and restrictive data policies prevent client-side trial extensions and cross-tenant access.
- Workspace access and branding are scoped to the authenticated identity; access queries fail closed instead of turning errors into empty memberships.
- Server-function requests use framework CSRF middleware while preserving bearer authentication to reject cross-site mutations.- Task attachments are written only by server functions after permission checks, kept in a private bucket with soft delete and a SHA-256 trail, and copied best-effort to the organization's connected Google Drive; the project journey is read through one definer function that limits clients to their own or client-visible events.
- Project screens stay live through data-free broadcast events on private `project:<id>` channels emitted by database triggers; subscribers are authorized by realtime message policies and refetch through the existing permission-checked reads, with slow polling only as a fallback.

- The Dashboard has two views (Padrão | Funil, remembered per browser in `core_dashboard_view`). The funnel view is driven by per-pipeline "Objetivos do funil" stored in `app_config` as `funnel_goals:<pipelineId>` (read via `funnel-goals.server.ts`, saved by `saveFunnelGoals` after a pipeline access check): objective step = what counts as conversion, explicit stage → step/exit roles (default guessed by `classifyStage`), optional journey history (`lead_events` stage_changed) and funnel tags, custom labels and targets. `computeGoalFunnel` is pure, cumulative and tested. Its colors come from `funnelPalette(primary, ink)` (OKLab ramp from the logo’s dark color to the brand color, contrast-checked text), fed by `useBrandPalette`: the Appearance color wins, then the logo’s vivid color, then Core green.
- Pipeline header filters (Kommo-style panel: shortcuts, properties, tags) are pure in `board-filters.ts`: entry date period, origin keys (source, utm_source/medium/campaign, gclid/fbclid ad), stages (hides other columns), temperature (lead temperature or form classification), tags (any/all, configured + raw lead tags with counts) and open-task states from `listPipeline().leadTasks`. OR inside a group, AND across groups; remembered per pipeline in the browser (`core_pipeline_filters:<id>`).
- The Pipeline has Kanban and List views (`core_pipeline_view`, per browser). The list (`PipelineListView`) shows the same filtered leads as the board, sortable columns, inline stage change and bulk move through the existing `moveLead` (appended to the end of the target stage; single moves to a won stage open the win/convert dialog), with incremental "show more" paging.
- Project task messages: `task_comments.visibility` ('equipe' internal | 'cliente' shown in the portal) and `author_kind` (migration 23). Team inserts are always 'equipe' authors (RLS); the portal writes through `portal_add_comment` as cliente/cliente; `portal_project` only returns 'cliente' messages. Sending to the client from the Core makes the task visible in the portal and notifies the project's clients. `project_journey` reads messages from `task_comments` (with visibility; clients only see portal ones), and triggers copy task and project messages into the originating lead's `lead_events` (`project_message`, via `project_lead_ids`: `projects.lead_id`, lead converted into the project or its client).
- Project access links: team invites (and `resendTeamInvite`) always point to the Core project page (`coreProjectUrl`: current https origin, or `https://core.hublynx.com.br` when on a preview/local host); only client invites use `/portal/...`. A team account opening the portal gets a `TEAM_MEMBER:<id>` result and a button to the project in the Core.
- Project templates carry a team (`project_template_members`: person, department, role — default executor) and a per-task `assignee_user_id` (migration 24). Applying a template adds the team to the project (`team.server.ts` → `addTeamToProject`, granting only the Projects module) and assigns each task. Executors can only complete/date their own tasks (RLS + `canEditTask` in `RoadmapStages`).
- Project-only people (role user, Projects module, no CRM: `isProjectOnlyAccess`) see only Projetos and `/minhas-tarefas`; `AccessGate` redirects other pages and the sidebar shows only Projetos.
- Stage task rows: always-open message field (team/client destination, `task_comments`), editable start/due dates (`setStageTaskDates`), and deep links `?aba=etapas&tarefa=<id>` that open the stage and highlight the task (used by alerts, notifications, priority modal, pending details and e-mails via `task_link`/`taskPath`).
- Assigned-task notifications: DB trigger notifies the assignee on insert/assignment (bell, realtime sound + toast); `runTaskNotifications` e-mails each new assignment once and a daily digest (today + overdue, after 7h BRT) via the organization's connected mailbox (`sendOrgMail`), de-duplicated in `task_push_log`; it runs from the open app (≤10 min) and the cron route.
- Projects module on phones follows the approved "Projetos no celular" canvas: list with Minhas tarefas shortcut, search + filter toggle and status chips; project page with a sticky top bar (back, name, ⋯ actions), dark summary card (progress ring, Nova tarefa) and 2×2 indicators; stages always vertical with Todas/Minhas/Atrasadas filter, current stage auto-opened and task rows as cards with 44px controls; team cards with role + Reenviar acesso on their own row; journey composer sticky at the bottom. Desktop layouts are unchanged (all via `sm:`/`md:` variants).
- Projects module on computers (≥1024px) follows the approved "Projetos — desktop" canvas: list with summary line (projects needing attention, my late tasks), status chips at every size, initials cards with a rose outline when there are late tasks and a "N suas" chip, plus a sticky "Minhas tarefas" panel on xl; project page with breadcrumb and a dark summary band (progress ring, chips, 4 indicators, Nova tarefa); stages in vertical view become a left rail (grouped by phase, late badge) with the selected stage's pending tasks as prominent cards (`StageTaskCard`: state band late/today/on time/client, Sua/priority chips, responsible, dates, visibility, files, always-open message, green Concluir) and completed ones collapsed; the journey tab adds `ProjectTeamSidebar` (client + team with late/on-time status and resend access). Phones keep the mobile layout.
- Project cost sheets (Comercial tab) import Excel/CSV files: the browser reads the workbook with `xlsx` (CSV as raw text, UTF-8 with Windows-1252 fallback), `buildImportedSheet` (pure, tested) picks the header row and infers column types (text, number, currency, percent, date, Sim/Não) with Brazilian number/date formats, and `importSheet` creates one sheet per non-empty tab and inserts rows in batches (max 40 columns / 2000 rows, rolled back if rows fail). Without a department it creates "Planilhas" (empty).
- Stage task sequence: `tasks.position` keeps the template order inside each stage (applying a template sets position = template task order; new tasks go to the end), and stage tasks/portal list by position, then due date, then creation. Migration 25 backfills existing projects by matching stage name + task title to the project template. Desktop task cards are stacked one per row (list), with Concluir beside the message field.
- Light brand colors (dark text on them, e.g. Valesafe yellow set in Configurações › Aparência) switch the Projects module to the "vivid" look: `BrandTheme` sets `--band-*` (summary band in the brand color with navy text, navy Nova tarefa) and `--task-today-*`/`--task-ontime-*` (task card state bands in brand solid/soft); defaults in `styles.css` keep the navy band. Task cards show their sequence number and Concluir uses `--primary`.
- Project team on computers (≥1024px): `MemberTable` lists client and team one person per row with fixed shared columns (person name + e-mail, department, role select, open/late task status from the stage-tasks query, compact actions), plus search and "Com atraso" filter; cards remain below lg.
- Importing into an existing cost sheet tab ("Importar nesta aba", e.g. Compras › Itens comprados): `readWorkbook` reads values, formulas and number formats per cell; `buildImportedSheet` reuses keys/settings of same-named columns, drops trailing total rows (label "Total…" or column SUM → that column gets the footer sum), uses % / R$ formats for types and turns columns whose rows share one formula into calc columns (`calc.expr`, translated by `translateExcelFormula`: same-row refs, fixed cells as constants, SUM of a row range, ROUND/ABS/MIN/MAX; anything else stays a fixed value). `evalExpr` evaluates safely (no eval) and `calcValue(col,row,columns)` follows nested calc columns. A preview dialog shows columns, formulas, the first rows recalculated and totals; `replaceSheetFromImport` replaces or appends rows.
- Form-style spreadsheets (e.g. "SC - Carbografite" purchase request): the importer picks the header as the first row with at least half the titles of the fullest row and no "Campo:" labels, reads the table until the first blank row, drops the 1,2,3 "Item" column and template rows with only formulas, turns TODAY()-based status formulas into a `validity` column (Válido >180 · Atenção >90 · Ação >45 · Informativo >0 · Vencido, from a date column) and fills `cost_sheets.info` (migration 26): title + header fields above the table (label:value pairs), adjustments added to the total (single cells summed with SUM(...) in the "SOMA" row, e.g. substituição tributária and frete with note FOB) and notes (conditions; validity legend is shown automatically). Imported expressions treat empty cells as 0 like Excel. `SheetGrid` shows the editable header (`SheetInfoHeader`), validity chips and the summary (items total + editable adjustments = total geral), saved via `saveSheetInfo`.
- "Itens comprados" follows the Solicitação de Compras layout without re-importing: `upgradePurchaseSheet` (applied in `listProjectDepartments`) shows old-format sheets with `PURCHASE_COLUMNS` (same keys, + Situação do C.A. validity and ST, Valor total = Val. unit. × Quant. × (1 + IPI)) and `PURCHASE_INFO` (header fields, ST/Frete adjustments, conditions); migration 26 persists it. Cost sheets use a navy header row, highlighted total column, Total footer and underlined sheet tabs.
